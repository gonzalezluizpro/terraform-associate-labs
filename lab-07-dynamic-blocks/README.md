## Part 1 — Dynamic Blocks

### What Problem They Solve

Without dynamic blocks, 5 security group rules = 5 hardcoded `ingress {}` blocks.
A dynamic block replaces all of them with a single loop — generating repeated
**nested blocks** from a variable at plan time.

> Define the rules in a variable. Let the block generate the HCL. (**DRY principle**)

### Syntax

```hcl
dynamic "<BLOCK_TYPE>" {
  for_each = <collection>         # list, map, or set
  iterator = <optional_alias>     # renames the loop variable (defaults to block label)
  content {
    # reference alias.key or alias.value here
  }
}
```

### Dynamic Block Anatomy

| Part | Purpose |
| :-- | :-- |
| `for_each` | Iterates over a `list`, `map`, or `set` |
| `iterator` | Renames the loop variable — defaults to the block type (e.g. `ingress`) |
| `content {}` | **Required** — defines what each generated block looks like |
| `rule.key` | The map key or list index of the current item |
| `rule.value` | The full object value of the current item |

### Where Dynamic Blocks Work

| Context | Supported |
| :-- | :-- |
| `resource` blocks | ✅ Most common use case |
| `data` blocks | ✅ |
| `provider` blocks | ✅ |
| `provisioner` blocks | ✅ |
| `lifecycle {}` | ❌ Meta-arguments cannot use dynamic blocks |

## Full Code

### `variables.tf`

```hcl
variable "sg_ingress_rules" {
  description = "List of ingress rules for the security group"
  type = list(object({
    description = string
    port        = number
    protocol    = string
    cidr        = string
  }))
  default = [
    {
      description = "SSH access"
      port        = 22
      protocol    = "tcp"
      cidr        = "0.0.0.0/0"
    },
    {
      description = "HTTP access"
      port        = 80
      protocol    = "tcp"
      cidr        = "0.0.0.0/0"
    },
    {
      description = "HTTPS access"
      port        = 443
      protocol    = "tcp"
      cidr        = "0.0.0.0/0"
    }
  ]
}
```

### `main.tf`

```hcl
terraform {
  required_version = ">= 1.9"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "eu-west-1"
}

resource "aws_vpc" "lab" {
  cidr_block = "10.0.0.0/16"
  tags       = { Name = "lab-08-vpc" }
}

resource "aws_security_group" "dynamic_sg" {
  name        = "lab-08-dynamic-sg"
  description = "Security group built with dynamic blocks"
  vpc_id      = aws_vpc.lab.id

  # Dynamic block replaces N hardcoded ingress {} blocks
  dynamic "ingress" {
    for_each = var.sg_ingress_rules
    iterator = rule                 # renames loop variable from "ingress" → "rule"
    content {
      description = rule.value.description
      from_port   = rule.value.port
      to_port     = rule.value.port
      protocol    = rule.value.protocol
      cidr_blocks = [rule.value.cidr]
    }
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name      = "lab-08-dynamic-sg"
    ManagedBy = "Terraform"
  }
}
```

### `outputs.tf`

```hcl
output "security_group_id" {

  value       = aws_security_group.dynamic_sg.id
}

output "ingress_rule_count" {
```

## How the Dynamic Block Expands

With 3 items in `var.sg_ingress_rules`, Terraform generates exactly:

```hcl
# Generated at plan time — you never write these manually
ingress {
  description = "SSH access"
  from_port   = 22
  to_port     = 22
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]
}
ingress {
  description = "HTTP access"
  from_port   = 80
  to_port     = 80
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]
}
ingress {
  description = "HTTPS access"
  from_port   = 443
  to_port     = 443
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]
}
```

Adding a 4th item to the variable list → `terraform plan` shows **1 to add, 2 unchanged**.

## Part 2 — Provisioners

Provisioners are an **escape hatch** for running scripts when Terraform cannot manage
something purely declaratively. HashiCorp recommends avoiding them when possible —
use `user_data` for EC2 bootstrapping instead. They appear on the exam.

### The 3 Provisioner Types

| Provisioner | Runs On | Use Case |
|---|---|---|
| `local-exec` | Your local machine | Run Ansible, write a file, send a notification |
| `remote-exec` | The remote resource via SSH | Bootstrap software after EC2 creation |
| `file` | Copies to remote machine | Upload config files or scripts to EC2 |

---

### `local-exec` — Runs Locally

```hcl
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

  # Runs after create
  provisioner "local-exec" {
    command = "echo Instance ${self.public_ip} created >> deployed.txt"
  }

  # Runs on terraform destroy
  provisioner "local-exec" {
    when    = destroy
    command = "echo ${self.public_ip} destroyed >> deployed.txt"
  }
}
```

---

### `remote-exec` — Runs on EC2 via SSH

```hcl
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"
  key_name      = aws_key_pair.lab.key_name

  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("~/.ssh/id_rsa")
    host        = self.public_ip
  }

  provisioner "remote-exec" {
    inline = [
      "sudo yum update -y",
      "sudo yum install -y httpd",
      "sudo systemctl start httpd",
      "sudo systemctl enable httpd"
    ]
  }
}
```

---

### `file` — Copy File to EC2

```hcl
provisioner "file" {
  source      = "scripts/setup.sh"   # local path
  destination = "/tmp/setup.sh"      # remote path on EC2
}
```

> `file` and `remote-exec` both require a `connection {}` block.

---

### Provisioner Exam Rules

| Rule | Detail |
|---|---|
| Default trigger | Run at **create time** only |
| `when = destroy` | Run at destroy time instead |
| `on_failure = continue` | Ignore failure, continue apply |
| `on_failure = fail` | **Default** — failure marks resource as **tainted** |
| Tainted resource | Terraform **destroys and recreates** it on next apply |
| `null_resource` | No real infrastructure — exists purely to run provisioners |
| `terraform_data` | Modern replacement for `null_resource` (Terraform ≥ 1.4) |

---

### `null_resource` Pattern

```hcl
resource "null_resource" "run_script" {
  triggers = {
    always_run = timestamp()   # forces re-run on every apply
  }

  provisioner "local-exec" {
    command = "echo Running post-deploy script"
  }
}
```

---

## Common Exam Traps

| Mistake | Effect |
|---|---|
| `iterator = rule` but writes `ingress.value` inside `content {}` | Terraform error — must use `rule.value` |
| `dynamic "lifecycle" {}` | **Invalid** — meta-arguments cannot use dynamic blocks |
| Missing `content {}` block entirely | Syntax error |
| Using `for_each` on a `list` and removing a middle item | Index shift — use `toset()` or a `map` to avoid |
| Provisioner fails → `on_failure` not set | Resource is **tainted** and recreated on next apply |
| Using `remote-exec` without a `connection {}` block | Terraform error at apply time |
